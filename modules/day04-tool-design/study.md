# 白话讲解：工具设计——接口质量决定 Agent 上限

> 素材来源：DSH `docs/subsystems/tools.zh.md`、`docs/tool-execution-pipeline.zh.md`、`docs/cookbook/adding-a-tool.zh.md`、`docs/tool-catalog.zh.md`。

## 1. "浅工具"的真实代价

想象一个"读文件"能力，如果拆成"浅工具"会长什么样：模型得先调 `open` 拿一个文件句柄，再调 `seek` 定位到某个字节偏移，再调 `read(n)` 读一段字节，最后调 `close` 释放。这四连招会导致：

- 模型必须在 4 次工具调用之间正确传递状态（句柄、偏移量），任何一步算错（比如 seek 的字节数没考虑多字节字符编码）就会读到乱码或越界。
- 错误只会在最后一步才暴露，很难定位到底是哪一步错了。
- 4 次调用消耗 4 倍的上下文（4 组工具调用记录 + 4 组返回结果），却只换来 1 次真正有效的读取。

DSH 真实的 `read` 工具怎么设计？参数只有 `file_path`/`offset`/`limit` 三个，一次调用返回"带行号的内容"。模型只需要表达"要读哪个文件、从第几行、读多少行"这个**意图层面**的参数，不需要关心字节偏移这种实现细节。

## 2. 深工具 vs 浅工具：一个更危险的例子——"编辑文件"

如果没有专门设计，模型编辑文件的"自然"流程会是：先读全文 → 自己在自然语言层面定位要改的位置 → 自己拼出新文件内容 → 整体写回。这里藏着一个致命问题：**如果文件在"读"和"写"这两次调用之间被别的进程改动了**，模型手里的"心智快照"就和磁盘上的真实状态不一致，一次整体覆写会静默吞掉别人的修改。

DSH 的 `edit` 工具怎么设计？`old_string` 必须**恰好出现一次**才允许替换，否则直接失败（除非显式传 `replace_all: true`）。这不是"模型自己小心点"能解决的问题——是接口设计从根源上排除了"这次编辑到底改的是哪一处"的歧义。这正是"用设计定义掉特殊情况"：多义性编辑这种危险操作被设计成必须显式声明才能发生，而不是靠模型自觉。

**我们 MiniHarness 今天只做只读工具**（写操作和这类并发冲突问题要到 Day15 文件系统能力那天正式处理），但"深工具"这条设计原则从今天就要建立起来。

## 3. 一个工具由哪几块拼成

对照 `mini-harness/src/tools/types.ts` 里的 `ToolDefinition`：

| 字段 | 大白话 | 谁能看见 |
|---|---|---|
| `name`/`description`/`parameters` | 模型能看见的"说明书" | 模型 |
| `output.schema` | 工具承诺产出的规范数据形状 | 只给程序/未来的 run_code 用，不进模型请求 |
| `output.render(args, value)` | 把内部结构化值翻译成模型能看的文本——**纯函数**，只做"翻译"不做别的 | 翻译结果给模型看，函数本身不给模型看 |
| `execute(args, exec)` | 真正干活的函数体 | 谁都看不见，只有宿主调用 |
| `timeoutMs`/`isConcurrencySafe` | 只给宿主调度器看的元数据 | 模型永远看不到 |

**类比**：`name/description/parameters` 是"菜单上给顾客看的菜名和配料表"；`output.schema` 是"后厨保证端出来的菜必须长这样"；`execute` 是"后厨怎么做"，顾客完全不需要关心；`output.render` 是"服务员怎么给这道菜配文字说明"，跟菜好不好吃是两码事。

**为什么 `render()` 必须是纯函数、不能抛异常？** 因为它既服务实时流式渲染，也服务"回放一条历史工具调用"（会话重放的时候要重新跑一遍 render 把内容展示出来）。如果它有副作用或者会抛异常，你的会话历史就可能因为"重放的时候环境变了"而跟第一次执行时展示的内容不一致——这违反了"同一份日志重放两次结果必须一致"这条大原则（我们在 Day8-14 会正式碰到这条不变式）。

## 4. 工具执行管线：一步都不能让工具作者自己操心

`ToolRegistry.execute()`（`registry.ts`）把每次调用都推过同一条管线：

```
参数校验 → （检查取消：是否在派发前就已中止）→ 超时/取消赛跑 → tool.execute() → output.render() → ToolResult
```

- **参数校验**：不在 `execute()` 里手写，`ToolRegistry` 统一用 `validateArgs()` 校验，失败统一抛 `ToolArgsError`。
- **未知参数怎么处理**：`assertExplicitAdditionalProperties()` 在**定义期**（调用 `registry.define()` 的那一刻）就强制检查——每个 object 节点必须显式声明 `additionalProperties: true` 或 `false`，忘记声明直接抛错，工具都注册不进去。这是"用设计定义掉特殊情况"的又一例子：不是等到运行时收到一个多余字段才发现没处理，而是从一开始就不允许含糊的 schema 存在。
- **超时**：`timeoutMs` 是只给宿主看的元数据，由 `runWithTimeoutAndAbort()` 强制执行，工具作者不用自己写 `setTimeout`。
- **取消**：这里有一个我们在实现时真实踩到的坑，值得专门讲——见下一节。

## 5. 一个真实踩到的坑：取消检查的时机

写这份代码时，第一版是这样的：

```ts
const value = await runWithTimeoutAndAbort(tool.execute(rawArgs, exec), tool.timeoutMs, exec.signal)
```

测试写了一个"signal 已经提前 abort，工具体不应该执行"的用例，结果失败了——工具体里的 `ran = true` 还是被设成了 `true`。

**原因**：`tool.execute(rawArgs, exec)` 这个函数调用，在传进 `runWithTimeoutAndAbort` 之前就已经被求值了。调用一个 `async function` 会**立即同步执行它的函数体，直到第一个 `await`**——如果函数体在第一个 `await` 之前就有同步副作用（比如 `ran = true`），这段代码在我们检查 `signal.aborted` 之前就已经跑完了。

**修复**：把 `tool.execute(rawArgs, exec)` 换成一个"还没被调用的函数"（`() => tool.execute(rawArgs, exec)`），先检查 `signal.aborted`，确认没有取消，再真正调用它。

这正好印证了 Day6 会详细讲的"取消不是布尔值"——取消检查的**时机**和调用的**先后顺序**本身就是协议的一部分，不是随便放在哪里都一样。DSH 原文里"未开始的工具体应该跳过并标记 `ABORTED_BEFORE_DISPATCH`"这条规则，背后就是在防这类"看似检查了取消，实际上晚了一步"的 bug。

## 一句话总结

工具设计的核心矛盾是：**模型需要简单、意图层面的接口，而真实世界的操作充满了编码、并发、权限、超时这些复杂性**。DSH 的解法不是让模型变得更聪明去处理这些复杂性，而是把复杂性**下沉进工具内部和统一的执行管线**，让模型永远只看到"这次调用干净利落地成功了，或者干净利落地失败了，原因很清楚"。这是"深模块"哲学最直接的应用场景。
