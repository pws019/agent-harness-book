## 为什么 `Agent.compact()` 今天才第一次出现

Day13 `planCompaction()`/`applyCompaction()` 从写出来那天起就是纯函数，没有任何真实调用方——`agent-handle.ts` 的 `session` 字段是私有的，外部代码拿不到能喂给 `applyCompaction()` 的那个 `Session` 实例。这不是遗漏，是"今天只做确定性裁剪那一半"（`compaction.ts` 注释）的自然结果——写这条端到端演示,第一次真的需要"长上下文触发压缩"这一步落到一个真实 `Agent` 上,这个接缝才第一次被真正需要。补的时候顺手让 `applyCompaction()` 新增一个可选 `sink` 参数,跟 `closeDanglingActivity()`（Day9）同一个模式——不然压缩事件只会进内存,不会镜像进持久化 store。

## tsserver `references()` 超时问题的教训

写完 `graduation-demo.ts` 之后,`tests/tsserver-client.test.ts` 开始稳定超时——`ps` 实测确认 tsserver 进程当时 CPU 占用接近 0,说明不是"在算,算得慢",是卡住了；把超时从 5 秒加到 120 秒依然拿不到响应,排除了"只是需要更久"这个解释。二分排查确认这跟 `graduation-demo.ts` 具体写了什么内容无关（甚至跟这个特定的对比表达式无关——试过重写那一行代码,问题依旧），是 `Agent` 这个类到 Day30 为止的引用集合规模（几乎每个测试文件都 `import { Agent }`）本身触发了 tsserver 的某种性能病理——换一个引用数小得多、但依然满足"不止一处"的真实符号（`GoalStore`），同样的查询 10 毫秒级返回。**教训**：真实语言服务工具不是纯函数,它们的性能特征可能跟"这个查询本身有多难"完全无关,而是跟"整个项目当前的规模/状态"深度耦合——这正是这门课坚持"真实 IO、真实进程、不 mock"这条纪律的意义所在,如果 `tsserver-client.ts` 是靠 mock 测试的,这类真实环境问题永远不会被发现。

## 任务 2：可选链短路参数求值

`sink?.append(session.append(...))` 这个表达式,当 `sink` 是 `undefined` 时,ECMAScript 规范里可选链的短路行为不只是跳过 `.append(...)` 这次方法调用本身,是把**整个链式表达式**（包括还没求值的参数）一起短路掉——`session.append(...)` 这个参数表达式压根不会被执行。`node -e "undefined?.foo(console.log('evaluated') || 1)"` 跑一遍就能验证："evaluated" 根本不会被打印出来。这解释了为什么这次压缩"完全没发生过"：不是压缩逻辑本身错了,是`session.append()` 这个必须无条件执行的副作用,被一个只应该控制"要不要额外通知 sink"的可选链意外连带短路掉了。修复是拆成两条语句——先无条件求值 `session.append()`,再单独一行有条件地通知 `sink`,让"这个副作用一定发生"和"要不要额外转发"完全解耦,不再共享同一次短路判断。

## 任务 4：毕业问答（示范作答）

**1. 仅追加事件日志解决的问题**：一个能调用工具的聊天机器人,通常只需要维护一份"当前对话"的内存状态,崩溃了重启就丢了,不需要面对"崩溃后怎么诚实恢复"、"多个客户端怎么看到一致的进展"、"审计要怎么回溯某次副作用的完整决策链路"这类问题。这些问题的共同前提是：有一份**不会漂移、可以被任意多个视图独立派生**的真源——ADR-001 记录的正是这一点。今天的 `graduation-demo.ts` 第六阶段（模拟服务重启并恢复）能够成立,完全依赖这份日志确实是唯一真源这件事——如果 `Agent.history` 是单独维护的一份缓存,重启后就没有任何依据能重建它。

**2. fail-closed 与 fail-open 是同一个标准的两面**：`CommandPolicy`（Day18）求值出错时拒绝而不是放行,是因为一旦放行,后果是一次真实执行的、不可逆的子进程命令。`TsserverProvider`（Day25）查询失败时降级到文本搜索,不是因为"这次没那么重要",是因为放行的后果只是"查询结果精度打了折扣",本身不产生任何副作用。两者用的是同一把尺子——"这一步失败会不会导致不可逆副作用"——量出来的结果不同,不是两条互相矛盾的规则。

**3. 一个诚实记录缺口的例子**：`WorkflowRunner.cancel()`（Day27）保证自己的终态记账在有界时间内落定,但**不**保证被取消的子 Agent 底层真的已经完全停止运行——`Agent.dispose()` 内部 `await this.runLoopPromise`,如果子 Agent 的 adapter 完全不理会 `AbortSignal`,这个 `await` 会永远不 resolve,`forceCancel()` 选择不再等它。这条缺口在 `workflow-runner.ts` 的代码注释、`study.md`、`release-checklist.md` 第6/7条、这份 `failure-model.md` 里被反复提及,从没有被掩盖过。诚实记录本身是一种工程纪律,不只是文档礼貌——因为下一个要在这套系统上做决策的人（可能是六个月后的你自己）,如果不知道这条边界,可能会在一个真正需要"保证子任务已经彻底停止"的场景下,错误地信任 `cancel()` 提供了它实际上没有提供的保证,这种错误信任造成的后果,通常比"这个功能干脆没做"更隐蔽、更难排查。
