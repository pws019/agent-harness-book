# ADR-004：可审计的静态 workflow，不做执行中途动态生成

**状态**：已采纳（Day27）

## 背景

原始大纲提到三种编排风格：确定性业务代码、模型动态选择工具（Agent loop 从 Day5 起一直是这种形状）、模型生成 workflow 脚本并在执行中途分支。第三种风格更灵活，但要求在运行过程中重新调用模型、重新解释新生成的代码——这跟"执行前就能完整审查这次会做什么"这个目标直接冲突。

## 决定

`WorkflowNode`（Day27）是一棵在执行前就已经完整建好的静态树——`agent()`/`parallel()`/`pipeline()`/`phase()` 四个 DSL 函数只构建描述符，不执行任何东西（跟 `React.createElement()` 同一个形状）；`WorkflowRunner` 才是真正的执行者，且只能解释一棵已经完整存在的树，不能在执行中途往树上追加新节点。

## 后果

**好处**：`maxAgents` 能在任何子 Agent 真正启动之前，就对着完整的树做一次性检查（`countAgentLeaves()`）——如果树是边跑边生成的，这类检查只能变成"运行时数到第 N 个就拒绝"，挡不住"已经启动的那几个"。整棵计划树可以在执行前被记录、被人工审查，这是"可审计"这个目标能够成立的前提。

**代价**：`pipeline` 不支持"上一步的结果驱动下一步的任务内容"——每一步的 `task` 文本是脚本写死的，这是`day27-milestone-workflow-orchestration/study.md` 明确记录过的范围收缩，不是遗漏。真要做到"模型根据某一步的真实结果，动态决定接下来并行跑几个、跑哪几个子任务"，需要在这棵树的静态性和可审计性之间做新的权衡——这门课没有做,是刻意的边界。
