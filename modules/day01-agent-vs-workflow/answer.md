# Day 1 答案

> 对照 [README.md](./README.md)「今天要学会什么」和 [exercise.md](./exercise.md)「验收自查」逐条作答。Day1 没有代码，答案主要落在概念理解和 `docs/` 里已经写好的产物上。

## 今天要学会什么

**1. 分清「业务 Agent」「Agent Runtime」「Agent Harness」「Agent 平台」这四层**

用 study.md 的厨房类比：

- **业务 Agent** = 一张具体的点单——只是状态（目标、进度、完成条件），自己不含任何"怎么做"的逻辑。对应 MiniHarness 里的 `Agent` 实例 + 它持有的 `history`。
- **Agent Runtime** = 厨师脑子里那套跟做什么菜完全无关的通用循环（问模型→执行→更新状态→判断是否继续）。对应 `runTurn()`。**最容易踩的坑**：把它想成"先切菜再打蛋"这种固定菜谱——那是工作流，不是 Runtime。
- **Agent Harness** = 整套厨房，一切能力（工具、adapter、执行管线）都可插拔组合。DSH 本体的定位，MiniHarness 只做了其中一小部分能力（`llm/`/`tools/`/`core/`）。
- **Agent 平台** = 同一套厨房开成什么形态卖（web/headless/sdk/桌面应用）。MiniHarness 到 Day30 都不碰这一层。

**2."一切皆插件"是平台扩展策略，不是最小可用 Agent 的必要条件**

DSH 自己都有 `sdk-minimal` 这种不叠加完整插件树的 profile——说明连它自己都承认不是所有场景都需要完整插件化。MiniHarness 目前只有 `llm/`/`tools/`/`core/` 三个目录，其余等对应能力真正需要时才建，不提前搭空壳架构。

**3. 六维定义框架**

目标、环境、能力、状态、策略、完成条件——已经针对"只读代码库调查 Agent"这个毕业项目填过一遍，见 [docs/product-scope.md](../../docs/product-scope.md) 任务5的表格。核心记忆点：每一维都要给具体、可验证的描述,不能写"要安全"这种空话。

**4. 判断固定工作流还是 Agent loop**

判断清单是"开放度、错误代价、可测试性、权限、成本"五个维度：如果写代码那一刻就能把所有分支和终止条件想清楚，用固定工作流；只有当"下一步该做什么"依赖运行时才能确定的信息（模型的中间判断）时，才值得上 Agent loop，并且必须配套把关机制去兜住不可预测性带来的风险。完整的两套方案对比见 [docs/product-scope.md](../../docs/product-scope.md) 任务2。

## 验收自查

**每个任务都有可观察的完成条件**：见 [docs/task-catalog.md](../../docs/task-catalog.md)——10条应完成任务，每条都写了"完成判定"（比如"结论列出所有命中位置+判断依据，且明确说明搜索覆盖了哪些目录"），不是"回答看起来不错"这种模糊标准。

**哪些判断交给模型、哪些必须由确定性代码完成**：交给模型的是"下一步该读哪个文件、该不该继续深挖、什么时候证据够了写结论"——这些是开放式判断。确定性代码兜底的是：只注册三个只读工具（不给写权限）、单次调查轮次上限、敏感路径（`.env`/`*.pem`）在工具层直接拒绝、结论必须带文件引用的格式校验——这些不依赖模型自觉,是接口设计和执行管线层面的硬约束。

**ADR 里的权衡代价**：[docs/adr/001-agent-vs-workflow.md](../../docs/adr/001-agent-vs-workflow.md)明确写了选 Agent loop 的代价——成本更高（多轮模型调用）、不可全量快照测试（换成日志重放+结构校验）、错误来源不可穷举（模型判断错误没法靠改逻辑修，只能靠运行时把关降低影响）、调试更难（要先分清是模型、工具、还是策略的锅），不是只列 Agent loop 的好处。
