# 白话讲解：Agent、Agent Runtime、Agent Harness、Agent 平台

> 素材来源：DSH（`deepseek-ai/deepseek-harness`）官方文档 `README.zh.md`、`docs/architecture.zh.md`、`docs/glossary.zh.md`。这个项目是真实存在、目前 215k+ star 的开源 Agent Harness（不是我瞎编的示例项目），下面所有引用都能在这三篇原文里找到。

## 1. 为什么要分层：不分层会踩什么坑

大部分人学"做 Agent"，第一反应是抄一个 while 循环：拼 prompt → 调模型 → 解析工具调用 → 执行 → 把结果塞回去 → 循环。这个循环本身没问题，问题是**没人告诉你这个循环该长在哪一层**，于是很多人把"循环怎么跑""状态怎么存""这次操作要不要审批"全揉在一个函数里。

后果是什么？DSH 架构文档里有一句话很好地点破了根因：

> "模型可见即已记录。抵达模型请求的一切都必须能从日志重建，并由一项运行时不变量断言这一点。"——`docs/architecture.zh.md`

如果状态存储、循环调度、权限策略全部粘在一起，你就没法单独替换其中一层去做测试、重放或者加装策略——出问题了也分不清是模型的锅、工具执行的锅、还是权限策略的锅。DSH 的做法是把每一种"能力"都拆成一个可插拔的插槽（架构文档里管这个叫 seam），好处是显而易见的：

> "seam 正是替换一个提供方就能改变整个产品的原因。文件系统与进程提供方共享同一个执行世界，因此把它们指向远程沙箱，也就把 Bash、PTY 和 LSP 一并搬了过去，无需提供方专用 fork。"——`docs/architecture.zh.md`

**对你意味着什么**：不分层的代价不是"代码丑"，而是"你没法只换一层就复用整个系统"。比如你以后想把"本地执行工具"换成"沙箱里执行"，如果文件访问和命令执行的代码散落在业务逻辑各处，你就得到处改；如果它们从一开始就走统一的接口，你只需要换掉背后那一个实现。

## 2. 四层边界：用"厨房"类比讲清楚

DSH 天然就有四层结构，跟"厨师现在在做的这道菜 / 厨师脑子里的操作流程 / 整个厨房设备 / 最终开成什么样的门店"这个类比严丝合缝。

### 2.1 业务 Agent ——"厨师正在做的这一道菜"

这是"一次具体任务的实例"：有自己的进度、有自己的完成标准，但它本身不是一套可复用的机制。DSH 里对应的是 `Agent` 接口的一个实例，以及附着在会话上的**目标（goal）**：

> "**目标**：附着在现有会话上的单个持久完成目标，带有按修订号演进的 `active`/`paused`/`blocked`/`complete` 阶段和 Goal Round 上限……目标是一种状态，不是调度器，也不是一段独立对话；会话日志仍是其真源。"——`docs/glossary.zh.md`

### 2.2 Agent Runtime ——"厨师脑子里那套操作流程"

这是纯粹的"循环调度逻辑"：什么时候该请求模型、什么时候该执行工具、什么时候判定这一轮该结束。它不关心"工具从哪来""要不要审批"——那是下一层的事。DSH 里对应 `core/agent-loop`，也就是实现 `Agent` 接口的默认驱动器：

> "一个**步骤**是一次模型请求加上它调用的工具。一个**轮次**包含零个或多个步骤：它在领取首条输入之前打开，并在不再欠下任何工作时关闭。"——`docs/architecture.zh.md`

这句话里藏着一个很重要的判断标准：轮次什么时候关闭，不是"模型说完了"就完了，而是"不再欠下任何工作"——这是个系统判断，不是模型自报。我们 Day5 会具体实现这个逻辑。

### 2.3 Agent Harness ——"整套厨房，所有厨具都可拆卸替换"

**这才是 DSH 这个项目本身的定位。** 它 = 一个通用组合内核（Cordis）+ 一整套可插拔的能力插槽（工具、文件系统、shell、LLM 适配器、沙箱、审批策略……）+ 把这些零件拼装成一个可运行程序的机制。

> "DeepSeek Harness（`dsh`）是……开源 agent harness（智能体框架）。它构建于**一切皆插件**的架构之上，由 Cordis 驱动……"——`README.zh.md`

> "不存在需要打补丁的特权内核：扩展 dsh 的方式是把插件挂载到其他插件旁边，而各项注册都是副作用，会在其插件卸载时撤销。"——`docs/architecture.zh.md`

Harness 的价值不是"能跑一个 agent"，而是"提供一整套可替换、可组合的零件，让你能拼出不同形态的运行环境"。这句话精彩的地方在于，它把"一切皆插件"从一句口号变成了一个可验证的工程约束——**注册的副作用必须能在插件卸载时撤销**，不是为了看起来现代才这么设计。

### 2.4 完整 Agent 平台 ——"同一套厨房，开成快餐窗口 / 正餐堂食 / 加盟配送"

这是厨房之上再包一层、面向终端用户/开发者的产品形态。DSH 对应的是不同的 **profile**（web / headless / sdk / sdk-minimal / acp）和具体应用（`dsh web` 服务器、Electron 桌面应用、SDK）：

> "随附应用是 `dsh web`……`dsh --profile headless`、`dsh --profile sdk`、`dsh --profile sdk-minimal` 与 `dsh --profile acp`。"——`docs/architecture.zh.md`

同一套 Harness 内核，可以开成"一次性运行不留服务器"的命令行工具（headless），也可以开成"带 UI 实时重载"的 Web 服务（web），也可以"打包成半成品给别的产品集成"（SDK）。厨房设计没变，面向的终端消费场景完全不同。

### 一句话总结四者边界

| 层级 | DSH 对应 | 关注点 |
|---|---|---|
| 业务 Agent | `Agent` 接口实例 + 目标(goal) + 会话 | 这一次具体在做什么，做到哪了 |
| Agent Runtime | `core/agent-loop` | 循环怎么调度：何时请求模型、何时算一轮结束 |
| Agent Harness | Cordis + 全部能力插槽 + 组装机制 | 有哪些能力零件、怎么组装、怎么替换 |
| Agent 平台 | web / headless / sdk / acp / 桌面应用 | 最终交付给谁、以什么形态运行 |

**关键提醒**：我们接下来 30 天要搭的 MiniHarness，目标是 Runtime + 一小部分 Harness 能力（工具、会话日志、策略），**完全不需要碰第四层"平台"，也不需要一上来就做"一切皆插件"**。DSH 团队自己都留了一个例外口子——`sdk-minimal` profile 不叠加完整插件树，而是自己声明一棵精简的配置树，这说明连他们自己都承认：不是所有场景都需要完整插件化。

## 3. 六维定义框架：用一个具体例子过一遍

以"一个只读代码调查 Agent"（比如"帮我看看这个仓库里 auth 模块的调用链，写份分析，不许改代码"）为例：

| 维度 | 这个例子里是什么 | 呼应 DSH 的哪个机制 |
|---|---|---|
| **目标** | 产出一份 auth 模块调用链分析文档；如果调查中发现关键文件缺失，应该标记"阻塞"并说明原因，而不是硬编一个结论 | 「目标」有 `active/paused/blocked/complete` 四态，不是只有"完成"和"没完成"两态 |
| **环境** | 这个仓库的文件系统快照（只读挂载），不给任意 shell 执行权限 | 能力提供方共享同一个"执行世界"，可以指向本地或远程沙箱 |
| **能力** | 只注册"读文件""搜索代码"两个工具，明确不注册"写文件""执行任意命令" | 能力集合本身就是安全边界，不是靠"模型答应不做" |
| **状态** | 已经读过哪些文件、已经积累的调用链片段，全部持久化，中断后能从日志接着调查 | "模型可见即已记录"——会话日志是唯一真源 |
| **策略** | 单次调查最多几轮工具调用（避免无限翻文件）；碰到 `.env` 之类敏感文件跳过不读 | 审批与沙箱策略、轮次上限控制 |
| **完成条件** | 覆盖了 auth 模块所有入口文件 + 产出了结构化文档，两者都满足才算完成，不是"模型觉得可以停了" | 轮次要在"不再欠下任何工作"时才关闭，不是模型自称完成就完成 |

这六个维度不是我凭空发明的分类——"能力"和"环境"直接对应 DSH 的能力插槽机制，"完成条件"直接对应轮次关闭的判断逻辑。**练习里你要为自己选的毕业项目也填一遍这张表。**

## 4. Agent vs Workflow：什么时候该用哪个

DSH 术语表里有一条关于 **Ralph 循环**（一种特殊的全新 agent 运行模式）的定义，专门强调了它"不是"什么：

> "Ralph 循环：一次面向不可变目标的前台全新 agent 工作流运行……不是同会话目标、agent loop（智能体循环）模式、调度器或通用工作流脚本功能。"——`docs/glossary.zh.md`

连 DSH 自己的设计者都要专门强调"这不是 agent loop，也不是通用工作流脚本"——说明这几种东西在他们的心智模型里本来就是分开的，不能混用。结合"轮次/步骤"机制（轮次数量不固定，直到不再欠下工作）和工具执行要经过前置/后置检查这些细节，可以整理出一份可操作的判断清单：

| 判断维度 | 倾向"固定工作流"就够 | 倾向要上"Agent Loop" |
|---|---|---|
| **开放度** | 步骤数量、顺序、分支写代码时就能枚举完 | 需要模型根据中间结果动态决定下一步调用哪个工具、要不要继续 |
| **错误代价** | 单步错误容易发现且代价低，能用固定断言/单测覆盖 | 错误可能出在"模型自己选错了工具/参数"这种没法穷举校验的地方，需要运行时把关（执行前后检查、审批）兜底 |
| **可测试性** | 输入输出可预测，容易写确定性测试 | 依赖日志重放做事后验证，靠可观测性而不是可预测性保证质量 |
| **权限/风险面** | 所需权限单一固定，不需要按上下文动态调整 | 需要按场景动态收窄/放开能力 |
| **成本** | 一次调用/一条流水线就能完成 | 需要多轮试错才能收敛，靠"多次尝试"换"探索空间覆盖" |

**一句话总结**：如果你在写代码那一刻就能把所有分支和终止条件想清楚，用固定工作流——更便宜、更可测、错误代价可控。只有当"下一步该做什么"本身依赖运行时才能确定的信息（模型的中间判断）时，才值得上 Agent loop，并且必须配套把关机制（执行前后检查、审批策略）去兜住这份不可预测性带来的风险。

这也是为什么原 30 天大纲里第一天就要求你写两套设计方案（固定工作流版 vs Agent loop 版）再比较——**先证明"这个任务真的需要 Agent"，而不是默认所有任务都要上 Agent。**
