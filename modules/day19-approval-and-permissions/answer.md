# Day 19 答案

> 对照 [README.md](./README.md)「今天要学会什么」、[exercise.md](./exercise.md)「验收自查」和其中的思考题逐条作答。

## 今天要学会什么

**1. 三种交互类型为什么不共用 yes/no**

信息缺失（`question`）、偏好选择（`choice`）、风险审批（`approval`）对用户来说是完全不同的 UI（输入框/选择器/批准按钮），对系统来说风险等级也完全不同——批错一个偏好顶多重问一次,批错一次审批可能是真的执行了一次危险操作。用一个封闭联合类型（`UserInteractionRequest`）显式区分,调用方能从类型上直接判断该展示哪种交互,而不是共用一个 `{ prompt: string }` 然后自己猜"这次到底是哪种"。

**2. `argsHash` 和 Day15 `expectedHash` 是同一种手法**

两者都是"用一个指纹代表某个时刻的具体版本"（乐观并发控制）——`edit_file` 的 `expectedHash` 代表"我读到的这份文件内容"，`ApprovalRequest.argsHash` 代表"我批准的这一组具体参数"。写入/执行前重新算一遍当前的指纹,跟当初记录的比一比，对得上才放行,对不上就拒绝——不是加锁阻止别人动,是"检测到不一致就明确拒绝"。

**3. `consume()` 四个校验各防哪种故障**

见 study.md 第2节的表格：nonce 存在性防"凭空编造"；未消费防"重放/双击批准"（两者是同一种调用序列,同一条防线）；未过期防"过期回复"；参数哈希匹配防"批准后换参数"。

**4. 为什么今天不改 `runTurn`**

跟 Day15 `edit_file`、Day16 `run_command` 写完先不接 `cli.ts` 是同一个模式：先独立证明机制本身是对的（能挡住每一种原始大纲点名的故障场景），再决定怎么接进真正的调用方。把"发明审批机制"和"改造一个已经稳定运行 14 天的核心循环"拆开做，任何一边出问题都更容易定位是哪一半的锅——真正的接入放到 Day21 milestone，那时候有 `edit_file` 这个具体场景作为落地的靶子。

## 验收自查

**为什么把 `entry.consumed = true` 挪到过期/参数校验之前会破坏设计，具体是哪里失败的**：亲手挪过一遍（[exercise.md](./exercise.md) 任务1）——只有"故障注入2：批准后换参数"这一条测试失败,其它测试都不受影响。原因：把标记消费的动作提前到参数校验之前,意味着**哪怕这次调用的参数是错的（跟批准时不一致），nonce 也已经被标记成"用过了"**。测试里先用错误参数调用一次 `consume()`（预期应该失败,但会顺带把 nonce 烧掉),再用原本正确的参数重试——这次重试遇到的不再是"参数应该匹配、应该成功",而是命中了"是否已消费"这条检查（此时确实已经被标记成 `true` 了),抛出 `ApprovalAlreadyConsumedError`,而不是预期的成功。"重放"/"双击批准"两条测试之所以不受影响,是因为它们本来就是"用同一组正确参数消费两次"，标记消费的时机往前挪一点，并不改变"第二次一定会撞上已消费检查"这个结果。

**任务3：重复发起审批请求算不算资源耗尽，限制该放哪一层**：算——如果 `ApprovalStore.create()` 来者不拒,模型（或者被 prompt injection 操纵的模型）完全可以疯狂创建审批请求,哪怕最终都不会被消费,光是这些记录本身也会无限占用内存,这跟 Day17 思考题里"`JobRuntime.start()` 没有并发数量上限"是同一类问题。这个问题其实要拆成两层来看：

- **"同时存在多少个还没被消费/过期的请求"这个纯计数上限**，应该放进 `ApprovalStore.create()` 内部——理由跟 Day17 一样：`ApprovalStore` 是唯一真正知道"现在有几个请求还挂着"的地方（它自己的 `requests` Map），把计数检查放在它内部,任何调用方都躲不掉这条规则，不需要在外面重新查一遍它已经掌握的信息。
- **"同一个具体动作被反复请求、反复被拒绝，应该降级成直接拒绝不再问"这种更聪明的行为**，`ApprovalStore` 今天的状态**不够用**——它只记录"消费过没有"，完全没有记录"曾经被明确拒绝过几次"这类决策历史（`consume()` 目前只有"成功"和"抛异常失败"两种结果，没有一个专门的"用户主动拒绝"路径）。这一层判断需要的是"这个 session/这个 Agent 到这一刻为止,针对这个具体动作,过去做出过什么决策"这种更宏观的历史视角,天然属于以后要把审批接进 `runTurn` 的那一层（Day21），而不是 `ApprovalStore` 自己该管的事——`ApprovalStore` 的职责边界就是"管好当前还活着的这些请求",不该往上扩展成"记住并分析所有历史决策模式"。
