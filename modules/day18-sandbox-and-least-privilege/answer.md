# Day 18 答案

> 对照 [README.md](./README.md)「今天要学会什么」、[exercise.md](./exercise.md)「验收自查」和其中的思考题逐条作答。

## 今天要学会什么

**1. 策略判断和强制执行为什么要分开**

`CommandPolicy.isAllowed()` 是一个纯函数式的判断，自己不 spawn、不碰文件系统；真正拒绝一次调用发生在 `bash-tool.ts`/`job-tools.ts` 的 `execute()` 里——判断说不允许就直接 throw，没有第二条路能绕过。分开的好处：`CommandPolicy` 可以完全独立测试，不需要真的启动进程；以后想换判断规则（比如从固定白名单换成读配置动态判断），只需要换一个 `CommandPolicy` 实现，`execute()` 一行不用改。

**2. fail-closed：为什么策略出错要拒绝，不能默认放行**

如果策略求值出错时默认放行（fail-open），任何能让策略抛异常的手段（配置文件损坏、策略实现有 bug）都会变成一条绕过所有限制的捷径——攻击者不需要正面破解判断规则，只需要想办法让它出错。`FailClosedCommandPolicy` 把"策略不可用"和"sandbox 不可用"当成同一种情况处理：能力失效时选更保守的一边。

**3. 威胁模型的六个部分，以及诚实记录缺口**

资产/信任边界/攻击者/入口点/影响/缓解措施——见 [threat-model.md](./threat-model.md)。核心纪律是"已验证的"和"接受的缺口"用完全不同的写法：前者写清楚落地位置、能追溯到具体代码；后者写清楚为什么没做、真要做需要什么，绝不能把"没解决的问题"包装成"已经缓解"，那样文档就从"帮你发现问题"变成了"帮你掩盖问题"。

**4. 为什么不做真正的 OS 级沙箱**

容器/网络 namespace/seccomp 这类真正的隔离需要引入新的运行时依赖，跟项目至今零外部运行时依赖、跑在开发者本机的定位不符,而且原始大纲自己承认"DSH 当前 sandbox seam 主要约束文件系统效果，不自动覆盖网络或进程可见性"——连 DSH 自己都没做到完整隔离，MiniHarness 没必要假装做到了。

## 验收自查

**`tests/command-policy.test.ts` 和 `tests/red-team-regression.test.ts` 关于 fail-closed 的测试分别验证什么层次**：亲手把 `catch { return false }` 改成 `catch { return true }` 跑了一遍（[exercise.md](./exercise.md) 任务1），两条测试都会失败,但验证的层次不一样：

- `command-policy.test.ts` 直接 `new FailClosedCommandPolicy(broken)` 调 `.isAllowed()`，验证的是**这个类自己的行为**——不经过 `run_command`/`ToolRegistry`，纯粹测这一个函数的输入输出对不对。
- `red-team-regression.test.ts` 通过 `registry.execute('run_command', ...)` 走完整条链路，验证的是**这个策略真的被接进了工具执行路径、真的能拦下一次调用**——即使 `FailClosedCommandPolicy` 这个类本身写对了，如果 `bash-tool.ts` 的 `execute()` 忘了调用它（比如只是把 `policy` 参数存起来但从没读过），单元测试会全绿，只有这条端到端测试能发现"策略压根没被真正强制执行"。

两个都需要，是因为"这个类本身对不对"和"这个类是不是真的在生效"是两个不同的、都可能单独出错的问题——跟 Day9 `closeDanglingActivity` 忘了转发进 sink 是同一类教训:孤立测试组件本身、和测试组件是否真的被正确接进整条链路,永远是两件事。

## exercise.md 任务3思考题：网络外传的"中间方案"

**一个代价不高、但确实能挡住一部分场景的方案**：给 `run_command`/`start_job` 的默认 env 加上指向一个不存在地址的 `http_proxy`/`https_proxy`（比如 `http://127.0.0.1:1`）。绝大多数遵守标准约定的 HTTP 客户端库（`curl`、Python `requests`、Node 的部分 HTTP 库）在发起请求前会检查这两个环境变量，如果配置了代理就会先尝试连接代理——代理地址连不通，请求直接失败，不会真的发出网络流量。

**这个方案能挡住什么**：绝大多数"正常调用标准 HTTP 客户端库发起请求"的场景——这覆盖了相当一部分"模型写一段调用某个 HTTP 客户端库发请求"这类不太刻意的外传尝试。成本极低：只是多设两个环境变量,不需要引入任何新依赖或运行时组件。

**这个方案挡不住什么**：任何**不查这两个环境变量**的网络路径——直接用底层 socket API 手写网络请求（不经过遵守代理约定的高层库）、DNS 查询本身（有些工具的域名解析不经过代理设置）、以及任何存心绕过代理约定的实现。这跟 `CommandPolicy` 挡不住"被允许的程序自己发网络请求"是同一类局限——它是一个基于"大多数程序遵守共同约定"的软性缓解，不是强制边界,真正的攻击者只要知道这条防线的存在就能绕开。威胁模型里如果要加这条,必须诚实标注"部分缓解，不是强制边界"，不能升级成"✅ 已解决"。
