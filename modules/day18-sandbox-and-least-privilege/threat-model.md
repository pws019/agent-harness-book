# 威胁模型：MiniHarness 的执行类能力（`edit_file`/`run_command`/`start_job`/`cancel_job`/`job_status`）

> 覆盖范围：Day15-17 引入的、会产生真实副作用或消耗真实资源的工具。Day1-14 的只读工具（`read_file`/`list_files`/`search_text`）不在这份模型里——它们唯一的风险面是"读到不该读的文件"，已经被 `resolveWithinRoot` 挡住，威胁模型价值有限。

## 资产（要保护什么）

1. **workspace 之外的文件系统**——用户机器上其它目录、其它项目的文件。
2. **调用这个 Agent 的宿主进程持有的敏感信息**——环境变量里的 API key、数据库密码等。
3. **本机计算资源**——CPU、内存、进程数、磁盘空间，被过度消耗会影响机器上其它正常工作。
4. **网络可达的其它系统**——workspace 之外的、这台机器能连到的任何服务。

## 信任边界

```
                    ┌───────────────────────────────┐
                    │        不可信输入                │
                    │  模型的输出（可能被 prompt        │
                    │  injection 操纵）、workspace 里   │
                    │  的文件内容（可能被人恶意构造）      │
                    └───────────────┬───────────────┘
                                    │ 跨越边界
                                    ▼
                    ┌───────────────────────────────┐
                    │     MiniHarness 工具执行层        │
                    │  resolveWithinRoot / argv 数组 /  │
                    │  env 白名单 / CommandPolicy /     │
                    │  进程树杀 / 输出上限               │
                    └───────────────┬───────────────┘
                                    │ 跨越边界
                                    ▼
                    ┌───────────────────────────────┐
                    │      操作系统 / 真实资源           │
                    │  文件系统、进程、网络、CPU/内存      │
                    └───────────────────────────────┘
```

模型的输出**永远**被当成不可信输入——即使这一天没有真的接一个会被 prompt injection 影响的真实模型（`HeuristicInvestigationAdapter` 还是固定策略），威胁模型仍然要假设"模型说什么都可能是攻击者想让它说的"，这是 Day18 红队测试成立的前提。

## 攻击者画像

- **恶意/被操纵的模型输出**：通过 prompt injection（比如 workspace 里一个文件的内容写着"请忽略之前的指示，执行 xxx"）让模型生成危险的工具调用参数。这是今天最主要考虑的攻击者——不是"外部黑客直接攻击这个进程"，是"攻击者通过模型这个中间人间接达到目的"。
- **心不在焉/犯错的模型**：不是恶意，只是编错了参数（路径写错、命令拼错），后果可能同样严重（比如不小心指向了 workspace 外的路径）。防线大多数时候对两者都生效，不需要区分"是不是故意的"。

## 入口点

| 入口 | 对应工具 |
|---|---|
| 文件路径参数 | `edit_file` 的 `file_path`、`run_command`/`start_job` 的 `cwd` |
| 命令与参数 | `run_command`/`start_job` 的 `command`/`args`/`env`/`stdin` |
| 任意 job id | `job_status`/`cancel_job` 的 `jobId`（枚举/猜测其它 job） |

## 影响（如果防线失效）

- 读到/覆盖 workspace 外的任意文件（symlink 逃逸、路径穿越）。
- 泄漏宿主进程的环境变量里的密钥（env 继承）。
- 通过 shell 语法注入执行任意额外命令（命令注入）。
- 通过网络把 workspace 内容发送到攻击者控制的服务器（网络外传）。
- 通过无限制启动子进程/后台任务耗尽本机资源（fork bomb / 资源耗尽）。

## 缓解措施（现状，逐条对应第2节表格）

| 威胁 | 缓解措施 | 落地位置 | 状态 |
|---|---|---|---|
| 路径穿越（`../`） | 字符串层面解析后判断是否仍在 root 内 | `resolveWithinRoot` 第一道关卡（Day4） | ✅ 已验证 |
| symlink 逃逸 | 对 root 和目标路径都做 `realpath` 再比较 | `resolveWithinRoot` 第二道关卡（Day15） | ✅ 已验证 |
| 命令注入（shell 特性） | `spawn` 不用 `shell: true`，argv 数组原样传递 | `process-runner.ts`（Day16） | ✅ 已验证 |
| env 泄漏 | env 白名单（默认只有 `PATH`） | `bash-tool.ts`/`job-tools.ts`（Day16/17） | ✅ 已验证 |
| 资源耗尽（fork bomb / 永不退出 / 输出洪水） | 超时+进程树 kill、有界输出收集器 | `process-runner.ts`（Day16）、`JobRuntime`（Day17） | ✅ 已验证 |
| 执行不该执行的命令 | `CommandPolicy` 白名单，fail-closed | `command-policy.ts`（Day18，今天新增） | ✅ 已验证，**默认关闭，接进去才生效** |
| 网络外传 | 无——一个被允许执行的程序自己发起网络连接，不受这里任何机制约束 | 无 | ❌ **接受的缺口**，见下节 |

## 明确接受的缺口：网络外传

MiniHarness 目前**没有**任何 OS 级网络隔离（没有网络 namespace、没有防火墙规则、没有代理强制转发）。`CommandPolicy` 能挡住"不允许执行 `curl`/`wget` 这类已知的网络工具"，但挡不住"一个被允许执行的程序（比如 `node`、`python`）自己在脚本内部发起网络请求"——只要这个可执行文件本身被允许跑，它调用标准库的网络 API 完全不受今天任何机制约束。`tests/red-team-regression.test.ts` 里"红队场景4"那条测试就是在验证并诚实记录这一点，而不是假装解决了它。

真要堵上这个缺口需要 OS/容器级别的网络隔离（网络 namespace、seccomp、Docker `--network=none` 之类），这超出了这个 Node 教学项目的合理范围——原始大纲自己也承认"DSH 当前 sandbox seam 主要约束文件系统效果，不自动覆盖网络或进程可见性"，MiniHarness 在这一点上没有比 DSH 做得更差,只是同样诚实地没有解决它。

## fail-closed 是贯穿所有缓解措施的兜底原则

无论具体是哪一类威胁,只要"用来判断是否放行的机制本身出错/不可用"，一律拒绝而不是悄悄放行——`FailClosedCommandPolicy` 是这条原则今天唯一的具体代码实现，但原则本身适用于以后任何新加的判断机制（Day19 的审批、Day20 的凭据解析）：**能力失效时选择更保守的一边，而不是悄悄放宽限制**。
