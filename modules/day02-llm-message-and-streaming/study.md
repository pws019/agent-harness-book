# 白话讲解：消息模型与流式协议

> 素材来源：DSH `docs/subsystems/llm-streaming.zh.md`（1086行）、`docs/agent-lifecycle.zh.md`。

## 0. 前置知识：流式协议到底是怎么回事（面向没做过后端的读者）

如果你用过 ChatGPT/Claude 网页版，文字一个字一个"打字机"式蹦出来——这就是流式响应，跟前端常见的 SSE（Server-Sent Events）或 `fetch` 读 `ReadableStream` 是同一类技术。

**为什么要流式**：模型生成一个长回答可能要十几秒。等它全部生成完再一次性 HTTP 响应返回，用户就要盯着白屏等。流式的做法是：模型每生成一点内容，服务端就立刻通过同一个还没关闭的 HTTP 连接推给你，这就是"逐字蹦字"效果的来源。

**传输层长什么样**：provider 的流式 API 底层基本都是 SSE——一个普通 HTTP 响应，`Content-Type: text/event-stream`，服务端不关闭连接，持续往里写数据，每条消息形如：

```
data: {"type":"content_block_delta","delta":{"text":"Hello"}}

data: {"type":"content_block_delta","delta":{"text":" world"}}

data: {"type":"message_stop"}

```

每行 `data: ...` 是一个事件，`\n\n` 分隔。

**"分片"其实叠了两层，容易混**：

- **网络层分片（TCP/HTTP 层面）**：一条 SSE 消息可能被 TCP 拆成好几个包，或者反过来好几条消息粘在一起到达。这一层通常由 HTTP 客户端库/浏览器帮你缝合好了，你拿到的是一行一行完整的 `data: ...`，不用自己处理。
- **业务层分片（下面 `StreamChunk` 这一层，我们代码真正要处理的）**：就算拿到一条完整的 SSE 事件，它携带的内容本身也是模型故意拆碎的——因为模型是一个 token 一个 token 生成的，"Hello world"可能被拆成 `"Hello"` 和 `" world"` 两条事件分开发。工具调用参数更极端：`{"path": "a/b.ts"}` 可能被拆成 `{"path": "a`、`/b.ts"}` 好几条事件，中间任何时刻你手里都只有半截 JSON，直接 `JSON.parse` 会报错。

下面第 3、4 节讲的 `BlockAssembler` 就是解决**第二层**分片：把按 `index` 归属同一个内容块的碎片重新拼回完整文本/JSON，拼完才能用。第一层网络分片是 HTTP 客户端库的事，跟我们业务代码无关。

**为什么会有各种异常（畸形流、重复 finish 等）**：一次性 HTTP 请求"要么成功要么失败"，状态很简单；流式请求把"一次交互"拉长成了一连串持续几秒到几十秒、随时可能中断的事件——网络抖动会断连（对应"中断/取消"）、provider 服务端 bug 会发出不该发的东西（对应"重复 finish"）、适配器翻译逻辑写错会产生不认识的类型（对应"未知 chunk 类型"）。这正是下面说的"流式响应的本质复杂性来自网络分片和取消随时可能发生"。

## 1. 为什么不能直接把 provider 的流事件甩给上层

OpenAI 的流式事件和 Anthropic 的流式事件长得完全不一样：字段名不同、分片粒度不同、结束标记不同。如果 Agent loop、UI 渲染、日志记录这三处消费方都直接认 provider 的原始事件类型，换一个 provider 就要在三个地方同时改代码。

DSH 的解法是定义一个**封闭的**（closed）联合类型 `StreamChunk`，只有七种事件：`block-start`、`text-delta`、`reasoning-delta`、`tool-call-delta`、`block-end`、`usage`、`finish`。所有适配器必须把自己的 wire 协议"翻译"成这七种。原文强调这个联合类型是封闭的：

> "对 `type` 的 `switch` 以 `assertNever` 结尾，因此新增变体会在每个必须处理它的消费方处触发编译错误。"——`llm-streaming.zh.md`

**白话理解**：`assertNever` 是个小技巧——在 `switch` 语句最后写一个"这里永远不该执行到"的分支，如果以后有人往联合类型里加了新的 case 却忘记在这个 switch 里处理，TypeScript 编译就会直接报错，而不是留到运行时"某个事件类型悄悄没人处理、被吞掉"这种隐蔽 bug。这是"用类型系统消灭一整类错误"的经典手法。

## 2. 消息到底长什么样

一条消息（`Message`）不是一段字符串，是一个**内容块数组**。块类型至少有四种：

- `text`：可见文本
- `reasoning`：推理/思考过程，跟可见文本分开存放（这样 UI 可以选择性折叠）
- `toolCall`：`{id, name, arguments}`，`arguments` 是**原始 JSON 字符串**
- `toolResult`：`{toolCallId, content, isError?}`

**类比**：一条消息像一个快递包裹清单，不是"一句话"，而是"这次寄了几件东西、每件是什么类型"的结构化列表。

原文特别提醒：新增一种块类型的门槛很高——"仅当适配器、UI、压缩（compaction）和持久回放路径均支持某种新模态时，才将其纳入可合并扩展的 map"。意思是：如果你只在一个地方加了新类型，另外三个地方处理不了，数据会在某个环节悄悄损坏或让程序崩溃。**我们的 MiniHarness 今天只做 text / reasoning / toolCall / toolResult 四种，先把这四种在所有环节都打通，再考虑加新类型。**

## 3. 流协议：七种事件，一个组装器

`StreamChunk` 的七种事件里，最关键的两条规则：

1. **`block-end` 直接携带组装好的完整 `ContentBlock`**，消费方不用自己去拼——拼接工作全部收在组装器（下面讲）内部完成。
2. **工具调用的 `arguments` 全程是字符串，不是对象**。原文写得很明确："部分片段通过 `argumentsDelta` 流式传输；如果提供方返回的是已解析的对象，适配器在 `block-end` 时重新序列化为字符串。"

**为什么必须是字符串？** 因为中间态是不完整 JSON（比如流到一半只有 `{"path": "a/b`），你没法对它调用 `JSON.parse`——会直接抛异常。只有等这个块的所有分片都收齐、`block-end` 触发时，你才拿到一个完整、可以安全解析的字符串。**这是本模块练习里最容易踩的坑**：很多人会想"边流边解析"，但正确做法是"先攒够，再统一解析"。

## 4. `BlockAssembler`：组装器，类比"快递分拣员"

这是唯一共享的组装实现，负责把散乱到达的 `StreamChunk` 折叠回完整的内容块。可以想象一条传送带：碎片包裹（chunk）陆续到达，贴着同一个 `index` 标签的碎片要被分拣员收进同一个箱子，箱子封箱（`block-end`）以后才能出库，出库后这个 `index` 就算完结了。

组装器有一条重要的"安全阀"：

> "已被 `block-end` 关闭的 index 如果又收到 delta，会被忽略（视为畸形流），这样一个行为异常的适配器就不能无限增长内存或破坏一个已完成的块。"

这是典型的"用设计定义掉特殊情况"——不是靠上层写防御性代码去处理这种畸形数据，而是组装器本身就直接拒绝处理垃圾输入。我们练习里也要实现这条规则。

### 中断（interruption）时怎么办

如果流被打断（用户取消、连接断开），组装器要能回答"目前手上有哪些能用的内容"。规则是：

- 已经完整闭合的块（有 `block-end`）：保留。
- 还没闭合但已经有非空内容的**文本/推理**块：保留（标记为不完整），因为半句话总比什么都没有强。
- 还没闭合的**工具调用**块：**一律丢弃**。

原文的解释是："中断发生在派发执行之前，保留一个不完整的工具调用就必须伪造一个执行结果"——一个只有一半参数的工具调用，你没法真的去执行它，留着它只会制造"这个调用到底算不算发生过"的歧义。**丢弃，是唯一不会制造歧义的选择。**

## 5. 失败模式（今天练习会用到故障注入验证这些）

- **空 completion**：模型返回了 `finish: stop` 但没有任何内容块——这不是"正常完成"，是**可重试错误**。原文："空 completion 是可重试错误，而不是静默的成功结果。" 如果不这样处理，一条空白的 assistant 消息会静默存进历史，没人会发现哪里出了问题。
- **未知 chunk 类型**：因为 `StreamChunk` 是封闭联合类型，理论上不该出现；但如果适配器实现有 bug 发出了不认识的类型，组装器应该直接报错，而不是静默忽略。
- **重复结束事件**：有的 provider 会在流尾巴又发一条只含 usage 的分片。健壮的实现要"缓冲 finish/usage 直到流真正结束，再统一 flush"，而不是收到第一个 finish 就直接关闭组装器。

## 一句话总结

流式响应的本质复杂性来自"网络分片"和"取消随时可能发生"这两个事实，DSH 的做法是把这份复杂性**收进一个专门的组装器**，让上层（Agent loop、UI）永远只看到"完整的块"或"明确标记为中断"的块，不需要自己处理分片和畸形数据。这正是"深模块"哲学的体现：组装器接口很简单（喂 chunk 进去，随时能问它要当前状态），但内部承担了所有拼接、去重、防御畸形输入的复杂度。
