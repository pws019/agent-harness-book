# 白话讲解：上下文窗口与压缩

> 素材来源：DSH `docs/subsystems/compaction.zh.md`。今天是阶段二最重的一天——不只是加新代码，是第一次真正修改 `deriveMessages()` 这个从 Day8 起就没变过的核心派生逻辑。

## 0. 前置知识：为什么"压缩"不能是"删除"

模型能一次看到的上下文是有限的（"上下文窗口"）。对话很长之后，历史迟早会超过这个上限，必须想办法"变短"。最直觉的做法是"删掉旧的"——但 Day8 建立的核心原则是"仅追加日志是唯一真源"，删除历史事件意味着**这份日志不再能诚实回答"这段对话到底发生过什么"**——以后想审计、想回放、想排查"模型为什么这么回答"，缺的那段历史永远找不回来了。今天要学的解法是：**原始事件一条都不删，只是在派生"给模型看的历史"这一步，用一条摘要替换掉一段原始事件**。日志本身始终完整，变短的只是"喂给模型的那个视图"。

## 1. 三个新事件：只追加，不改写

```ts
'compaction/start': { readonly fromSeq: number; readonly toSeq: number }
'compaction/summary': { readonly message: Message }
'compaction/end': Record<string, never>
```

这是 Day8 study.md 提过的"声明合并扩展"第一次真正发生——`SessionEventPayloadMap` 这个接口又长出了三个新的 key，`Session`/`deriveMessages` 里所有原有的 `switch` 都因为 `assertNever` 兜底而被编译器逼着补上了新分支（这也是为什么这三个事件类型一加进来，好几个文件都要跟着改一遍——不是巧合，是"封闭联合类型 + assertNever"这套机制故意设计出来的效果）。

**`compaction/start`/`toSeq` 必须是已经存在的 seq**——`Session.append()` 校验 `toSeq < 当前日志长度`，你没法"声明压缩还没发生的未来"。

**为什么摘要这条 `Message` 整体标成 `role: 'assistant'`，即使内容里混着用户说过的话**：`planCompaction` 压缩的范围里 `user/message` 和 `assistant/message` 都会被摘要覆盖（[compaction.ts:38](../../mini-harness/src/core/compaction.ts#L38)），但 `Message.role` 只有 `'user' | 'assistant' | 'tool'` 三种，没有"系统生成的摘要"这个选项——摘要本质上既不是用户说的、也不是模型原本说的，是系统事后生成的一份浓缩叙述，必须在三个里选一个。选 `'assistant'` 是因为这样能让模型把它理解成"agent 自己对历史的一次陈述"；如果标成 `'user'`，模型会把这一整段（包括原本是模型自己说的话）误当成用户说的,在"这句话该归因给谁"这件事上制造混淆。但外层包装只能二选一，不代表内容本身可以不分你我地拼在一起——`facts` 数组给每一行都保留了原始 `role` 前缀（`user: ...`/`assistant: ...`），这是为了弥补"包装必须选一个角色"这个限制、不让说话人身份在摘要文本内部彻底丢失（如果只是无差别拼接文本，虽然没有删字，但"这句话原本是谁说的"这条信息还是会丢，跟"确定性裁剪不做有损压缩"这条承诺不完全对得上）。

## 2. `deriveMessages()` 从"单趟扫描"变成"两趟扫描"

这是今天对已有代码改动最大的地方,值得讲清楚为什么必须这样改。

**问题**：压缩事件永远追加在日志**末尾**（不改写历史），但它要替换的是日志**前面**的一段内容。如果 `deriveMessages()` 还是像 Day8-12 那样"从头到尾扫一遍，边扫边决定要不要往结果里塞消息"，扫到前面那些本该被压缩掉的消息时，压缩声明还没出现在后面——**单趟扫描的信息不够，扫到某条消息的那一刻，还不知道它以后会不会被压缩**。

解法：先完整扫一遍，收集"哪些 `(fromSeq, toSeq)` 区间最终被声明压缩了、摘要是什么"（`collectCompactionRanges()`），再走第二趟正式派生——这次每碰到一条 surface 事件，先查它的 `seq` 是否落在某个已收集的区间里，是的话跳过（区间里第一次遇到时改为插入摘要），不是的话按老逻辑处理。

## 3. 一个真实踩到的坑：重复压缩产生了互相重叠的区间

写"对同一段历史压缩两次会怎样"这条测试时，第一版直接翻车了：

```ts
export function planCompaction(events, options) {
  const surface = events.filter(isSurfaceEvent)   // 问题在这里
  // ...
}
```

`planCompaction` 只看"所有 surface 事件"，不知道哪些已经被压缩过。第二次调用时，它从头数起,把已经被第一次压缩覆盖过的那些事件**又**当成候选，算出一个新区间——这个新区间的 `fromSeq` 恰好跟第一次的 `fromSeq` **一样**（都是"最早那条事件"）。`deriveMessages` 判断"这段区间的摘要有没有插过"用的是 `emittedRangeStarts.has(range.fromSeq)`——两个区间共用同一个 `fromSeq`,第二个摘要被误判成"已经插过了"，直接消失，派生结果少了一条消息。

**修复**：`planCompaction` 先调用 `collectCompactionRanges()` 算出"已经被压缩覆盖的 seq"，规划新区间时把这些排除在外，只在**还没被压缩过**的 surface 事件里挑。这样连续多次压缩，产生的区间天然首尾相接、不会重叠。

**这个坑值得记住的地方**：又是一次"两个各自看起来正确的函数拼在一起才暴露的问题"——`planCompaction` 独立测试时（只压缩一次）完全正常，`deriveMessages` 独立测试时（只处理一个区间）也完全正常，只有"连续压缩两次、再派生一次"这种跨越多个函数调用的场景才会暴露。这是本课程反复出现的同一条教训在阶段二的最后一次印证。

## 4. "针藏在长历史中"：为什么这条测试对确定性压缩意义不大，但仍然值得写

DSH 原文用这类测试验证**模型摘要**（真的调一次模型去总结长历史）有没有把关键事实弄丢——模型摘要是有损的，可能真的会把不重要的内容和重要的内容一起丢掉。我们今天的 `planCompaction` 只做了"确定性裁剪"这一半（直接把原文文本拼起来当摘要，不调用任何模型），**天然不会丢任何文字信息**——所以这条测试对我们来说更像是"验证接线正确"，而不是"验证摘要质量"。

这不代表这条测试没有价值：它锁定了"目前这套确定性策略下,关键事实不会丢"这个事实，一旦你按 exercise.md 的要求换成一个真正做有损压缩的（哪怕是假的）摘要函数，这条测试就会变成真正有意义的质量守卫——它会在你的摘要函数把关键信息弄丢的那一刻立刻报红。**测试本身没变，但换了实现之后，它的价值会变得完全不同**，这也是为什么"先写测试锁定预期行为"值得在功能本身还很简单的时候就做。

## 一句话总结

今天最重要的不是"如何写一个摘要算法"（那是模型能力的问题），是"如何在**不删除任何历史事实**的前提下，让派生出来的视图变短"——三个新事件只追加、`deriveMessages` 两趟扫描、`planCompaction` 排除已压缩区间，三者合在一起保证了"原始日志永远完整、派生视图可以按需变形"这条 Day8 立下的承诺,即使在"内容要变少"这种看起来天然要删东西的场景下也没有被打破。
