## 验收自查

**"半行崩溃后续写更糟"那个坑的成因和修复方式**：

- **成因**：`load()` 正确识别出文件被截断（`truncated: true`），但只在**内存里**丢弃了那半行垃圾——磁盘上那条没有结尾换行符的损坏行原封不动留在文件末尾。等 `runInvestigation()` 第二次运行、开始往同一个文件里 `appendLine()` 新事件时，新的 JSON 被直接拼在了那条没有换行符的垃圾后面，两条本该独立的行粘成了一整行读不出来的乱码——原本只是"半行损坏"（还能安全恢复，`truncated: true` 之前的行都完好），一续写反而变成了整份日志读不出来。
- **修复**：给 `RawStore` 加了一个可选的 `truncateTo(count)`，`JsonlSessionStore.load()` 一旦发现 `truncated: true`，立刻调它把那条损坏的尾巴从**物理文件**上真正切掉，让文件在一个干净的边界上结束，后面的 `appendLine()` 才能安全地另起一行。
- **这个坑的共同模式**（跟 Day9 sink 转发漏、Day13 压缩区间重叠是同一类）：**"加载一份可能损坏的日志"和"继续往这份日志里写新内容"分别测都没问题，只有真的把两件事串起来做一遍集成测试才会暴露**——`tests/session-milestone.test.ts` 就是专门覆盖这条链路的测试。

## 任务4：毕业问答——为什么不能就用一个数组存聊天记录、每次整个覆盖写 JSON 文件

**1. 进程在"整个覆盖写"中途被杀会发生什么**

"整个覆盖写"典型做法是 `fs.writeFileSync(path, JSON.stringify(fullArray))`——这不是一个原子操作，进程在写到一半被杀，磁盘上留下的是一份**语法都不完整**的 JSON 文件，之前所有历史（包括写这次之前早就安全落盘过的内容）全部一起报废，没有办法区分"这次没写完的新内容"和"上次已经写完的旧内容"，因为它们被写进了同一个文件、同一次写入操作里。对比"仅追加"（Day9）：写入按事件为单位，一次只追加一行，进程被杀最多损失"正在写的最后一行"（`truncated: true`），之前每一行都是完整、独立落盘过的，能被诚实地识别和保留。

**2. 支持"统计面板 + 调查工具同时看同一份历史"，两种方案的代价**

覆盖写方案下，两个消费方要么各自维护一份自己的派生状态并保持同步（容易出现 Day10 study.md 提到的"UI 说完成了但发给模型的历史其实还差一条"这种漂移），要么每次都要重新读一遍并重新计算全部内容——没有"只读需要的部分"这个选项，因为文件里没有稳定的位置标记。仅追加日志方案下（Day10），`projectSummary()`/`deriveMessages()` 各自只挑自己关心的事件类型，读的是同一份 `events` 数组，不可能对同一份历史给出互相矛盾的答案；`queryEvents()` 还能用 `seq` 游标分页，不需要每次都处理全量数据。

**3. 历史需要压缩时，覆盖写方案怎么保证压缩失败不会把原始数据弄丢**

覆盖写方案要压缩，操作是"读全部 → 在内存里生成一份缩短后的新内容 → 覆盖写回同一个文件"——压缩逻辑本身如果算错了（比如 Day13 那种"重复压缩产生重叠区间"的 bug），错误的结果会直接覆盖掉原始数据，原始数据**没有第二份拷贝**，一旦覆盖就无法挽回。仅追加日志方案（Day13）从设计上排除了这种风险：压缩操作只是**追加**三条新事件（`compaction/start`/`compaction/summary`/`compaction/end`），原始事件一条都不删、不改——压缩规划算错了，最坏情况是派生出来的"给模型看的视图"不对，原始日志永远在那里、永远可以用修复后的规划重新派生一遍，不存在"压缩失败导致原始数据丢失"这种不可逆的后果。
