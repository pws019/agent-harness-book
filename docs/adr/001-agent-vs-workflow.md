# ADR-001: Agent vs Workflow

## 背景

毕业项目要做一个"给定代码仓库 + 自然语言问题，产出结构化调查文档"的工具。需要决定：这件事该用固定工作流（纯脚本、无模型参与决策）实现，还是该上 Agent loop（模型在运行时动态决定下一步读什么、何时收尾）。

## 考虑的方案

- **方案 A：固定工作流**——用关键词/AST 规则匹配相关文件，按固定算法拼装调用图，用固定模板渲染成文档。整个流程零模型调用，纯脚本跑完。
- **方案 B：Agent loop + 工具 + 策略**——只给模型注册"列目录/读文件/搜索代码"三个只读工具，由模型在每一轮根据已读内容自主判断下一步读什么、什么时候证据够了写结论，Runtime 负责问模型、执行工具、更新历史、判断轮次是否结束。

## 决策

选择**方案 B**，作为项目的核心运行方式；方案 A 的确定性算法（比如 import 关系拼接调用图）不丢弃，而是**下沉成方案 B 里模型可以调用的工具/辅助函数**，而不是两套并行的实现。

原因：毕业项目要处理的是"任意自然语言问题"，不是"调用链"这一种固定问题模板。方案 A 对固定问题模板（比如"画出 auth 模块调用链"）足够，但换一个问题（比如"哪些地方绕过 ORM 直接操作数据库"）就得重新写一套匹配规则——本质上是把"该读什么、该往哪个方向深挖"这种开放式判断硬塞进写死的规则里，规则会随着问题类型线性增长，无法穷举。这正好落在 study.md 判断清单里"开放度高、需要模型根据中间结果动态决定下一步"的一侧。

## 权衡与代价

选方案 B 要付出的代价，明确写出来：

- **成本更高**：每次调查要多轮模型调用（预计 5-15 轮），不是一次脚本跑完，实际花费和延迟都比方案 A 高一个数量级。
- **不可全量快照测试**：同一个问题模型可能走不同探索路径得到不同的中间过程，传统"给定输入固定输出"的快照测试用不上，测试策略必须换成"日志重放 + 结构校验（结论是否都有文件引用支撑）"，测试基础设施本身要多花时间搭。
- **错误来源变得不可穷举**：方案 A 的错误是"规则漏掉了某类文件"，补规则就能修；方案 B 的错误可能是"模型读错了文件、过早判断证据够了"，这类错误没法靠改代码逻辑修，只能靠运行时把关（轮次上限、强制引用格式校验、`blocked` 状态兜底）降低影响，无法根除。
- **调试更难**：出问题时要先分清是模型判断的锅、工具实现的锅、还是策略配置的锅，比方案 A 单纯看哪一步脚本报错要费劲得多。
- **确定性算法没有被浪费，但需要额外的封装成本**：方案 A 里"按 import 关系拼调用图"这类确定性逻辑要重新包装成一个模型能调用的工具，而不是直接跑，多了一层接口设计和参数校验的工作量。
